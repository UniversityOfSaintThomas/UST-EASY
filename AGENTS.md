## Fraud Monitoring Feature (ECRMSF-5511 / ECRMSF-5529) — Key Architecture Notes

Full design and status: `docs/fraud-monitoring-recaptcha-ip-geo.md`. Key things a future agent needs to know before touching this area again:

- **`Application_Login__c`** is the audit-log object — one row per Registration/Login/Submission event, per active `Application__c` the Contact has. Relates off **Contact**, not User.
- **Every fraud-monitoring capture path that does a callout (reCAPTCHA, geolocation) after prior DML in the same transaction must use `@future(callout=true)`** — this bit us twice in this codebase (Registration path, then the Submission trigger) before the pattern was consistently applied. See `ApplicationRegistration.logRegistrationAttemptAsync` and `ApplicationTriggerHandler.logSubmissionAttemptAsync` for the reference implementation, including the "capture headers synchronously before dispatching, never inside the future method" detail.
- **Graceful degradation is load-bearing for this feature**: `ReCAPTCHA_Score_Status__c` (Scored/Unavailable/Error) and nullable `ReCAPTCHA_Score__c`/`Geolocation__c` are the whole point — "Unavailable" must never be silently confused with "high risk" anywhere downstream (Flow, LWC, reporting). Both `Location_Match_Warning.flow-meta.xml` and `Fraud_Alert.flow-meta.xml` gate correctly on `Geolocation__c` not blank / `ReCAPTCHA_Score_Status__c = 'Scored'` before evaluating.
- **Submission events have no client-side JS hook yet** — `Client_Env_JSON__c` on Submission-type `Application_Login__c` rows will only ever have the server-merged `referer`/`userAgentMismatch` keys (both usually null, since there's no client-reported UA to compare), never the richer signal set (`webdriver`, `screenWidth`, etc.) that Registration/Login rows get. Fixing this requires finding which Visualforce page renders the final "Submit" action across the three known call sites (`ApplicationRequirement.cls`, `ApplicationChecklist.cls`, `ApplicationChecklistComponentController.cls`) and adding the same JS collection pattern used on `ApplicationRegistration.page`/`ApplicationLogin.page`.
- **Two Flows fire on the same trigger event** (`Application_Login__c` after-save Create, `Event_Type__c = 'Submission'`): `Location_Match_Warning.flow-meta.xml` (sets `IP_Location_Match_Warning__c`/`IP_Location_Match_Details__c` on `Application__c`) and `Fraud_Alert.flow-meta.xml` (sets `Shared_IP_Warning__c`, `Fraud_Review_Status__c`, and sends the alert email). **These two Flows do NOT rely on execution order relative to each other** — `Fraud_Alert` deliberately re-computes its own copy of the location-match comparison logic rather than reading `Application__c.IP_Location_Match_Warning__c` (which may not be updated yet if `Location_Match_Warning` hasn't run first). This is an intentional, documented logic duplication tradeoff — **if the location-match comparison/matching logic ever needs tuning, it must be updated in BOTH Flows**, not just one. See the global `agent-onboarding` skill for the general Flow-ordering lesson this is based on.
- **`Fraud_Alert.flow-meta.xml` has full fault-path handling** (added 2026-09-21, after the feature was originally declared complete): every `recordLookup`, `recordUpdate`, and the `emailSimple` action call have `faultConnector`s that write diagnostic detail to `Application__c.Fraud_Alert_Processing_Error__c` and/or send a technical-failure email to `Application_Setting__c.Fraud_Alert_Technical_Contact_Email__c` (a separate, fixed address distinct from the tunable `Fraud_Alert_Recipient_Emails__c` fraud-signal list). **A real, previously-undiscovered bug was found and fixed during this work**: the `Meets_Shared_IP_Threshold` decision had no `<defaultConnector>` at all, meaning the Flow interview silently ended right there whenever the shared-IP count was below threshold (the normal case) — the reCAPTCHA and location-mismatch signals had never actually been evaluated since the Flow was first built. Always check every `<decisions>` element in this Flow (and any Flow) for a genuine `<defaultConnector>`, not just a label, before trusting previously-verified behavior. Also confirmed: `emailSimple` faults are not always caught by their own `faultConnector` (a known Salesforce platform limitation, not a bug in this Flow) — this is a non-issue here only because `ApplicationTriggerHandler.logSubmissionAttemptAsync` (and the equivalent methods in `ApplicationLoginController`/`ApplicationRegistration`) already wrap their `Application_Login__c` inserts in their own `try/catch`, which is the real guarantee that a Flow failure never blocks a real applicant action.

## Google reCAPTCHA v3 — Enterprise Migration Trap

Google is mid-migration to "reCAPTCHA Enterprise"/"Fraud Defense." **New key registrations via the Cloud Console default to Enterprise**, which uses a different client JS API (`grecaptcha.enterprise.execute()`, not `grecaptcha.execute()`) and a different server verify API (Cloud REST, not classic `siteverify`) — incompatible with this project's classic v3 implementation, and Enterprise requires GCP billing (conflicts with the "free tier" requirement).

- **Symptom of an accidentally-Enterprise key/URL:** `Uncaught TypeError: grecaptcha.ready is not a function` in the browser console.
- **Correct classic v3 URLs (use these, not `enterprise.js` or a Cloud REST endpoint):**
  - Library: `https://www.google.com/recaptcha/api.js`
  - Endpoint: `https://www.google.com/recaptcha/api/siteverify`
- Config lives in `Application_Setting__c` (`reCAPTCHA_Site_Key__c`, `reCAPTCHA_Secret_Key__c`, `reCAPTCHA_Library_Url__c`, `reCAPTCHA_Endpoint__c`, `reCAPTCHA_v3_Score__c` threshold). A Remote Site Setting (`Google_reCAPTCHA`, `https://www.google.com`) is required for the callout — missing it manifests identically to the Enterprise-migration bug and the callout-after-DML bug (all three look like "score always Unavailable" with no visible error), so always check the `ReCAPTCHA_Error_Detail__c` diagnostic field for the actual exception before assuming which of the three it is.

## Geolocation — Hybrid Strategy

- **Login events**: use Salesforce's own `LoginHistory`/`LoginGeo` standard objects (free, no callout) — but only queryable **after** `Site.login()` succeeds, since the `LoginHistory` row doesn't exist until authentication completes. Query `LoginHistory` by `UserId` + a `LoginTime` window, follow `LoginGeoId` to `LoginGeo` for `City`/`Subdivision`/`Country`.
- **Registration and Submission events**: no Salesforce-native equivalent (not login actions) — use `ApplicationGeolocation.cls`, a shared utility calling ip-api.com's free tier.
  - **Plain HTTP, not HTTPS** (`http://ip-api.com/json/{ip}?fields=...`) — the free tier has no SSL. The Remote Site Setting (`ip_api_com`) needs `disableProtocolSecurity: true` for Salesforce to allow a non-HTTPS callout target at all.
  - **Rate limit: 45 requests/minute per SOURCE IP**, shared across the whole org's outbound callouts (all originate from Salesforce's IP ranges) — this is a much tighter, org-wide-shared budget than reCAPTCHA's per-key quota. On `HTTP 429`, return `null` immediately, don't retry.
  - **`status: "fail"` in the JSON body** (not an HTTP error) signals a bad/private/reserved IP — check explicitly, since 200 OK doesn't guarantee usable data.
  - Non-commercial use only per ip-api.com's terms.

## `Contact.Mailing_Lattitude__c`/`Mailing_Longitude__c` Are NOT Safe for Distance/Geo-Match Logic

`Contact` has custom formula fields (`Mailing_Lattitude__c`, `Mailing_Longitude__c`, `Geolocation_Coordinates__c`, `Distance_from_St_Thomas_Miles__c`) that echo the standard `MailingLatitude`/`MailingLongitude` fields — but all use `formulaTreatBlanksAs: BlankAsZero`. **A Contact with no mailing address on file at all reads these fields as literal `0, 0`** (a real point in the Atlantic Ocean, off the coast of West Africa), not as null/blank. Any distance-based or coordinate-based fraud/geo-match comparison built against these fields will treat "no address on file" as "lives near 0°N 0°E," making essentially every real-world submission IP look "very far away" — a serious false-positive trap for exactly the population (new applicants who haven't filled out a full profile yet, international applicants) this feature is supposed to avoid over-flagging.

**Fix used for the Location Match Warning Flow (task 17):** compare against the standard `MailingCity`/`MailingState`/`MailingCountry` text fields instead (via `CONTAINS(UPPER(...), UPPER(...))` substring checks against `Application_Login__c.Geolocation__c`), with an explicit `Applicant_Has_Mailing_Address` formula gate (`NOT(ISBLANK(MailingCity)) && NOT(ISBLANK(MailingCountry))`) that skips the comparison entirely — never sets a warning — when no mailing address exists. If any future work needs true distance/radius comparisons, do the null-check against the *standard* `MailingLatitude`/`MailingLongitude` fields directly (which are genuinely null when unset), not the custom `BlankAsZero` formula fields.

**Also note:** this org has **State and Country picklists enabled**. `MailingState`/`MailingCountry` (the free-text fields Flow formulas read) cannot be written to directly via DML/Apex when picklists are enabled — set `MailingStateCode`/`MailingCountryCode` instead (e.g. `'MN'`/`'US'`) and Salesforce derives the display text fields automatically. Attempting to set `MailingState` directly on this org fails with `FIELD_INTEGRITY_EXCEPTION: There's a problem with this state... Please select a state from the list of valid states.`

## EASY's Application Submission Architecture (No Single Submit Event)

There is no single, clean "application submitted" event in this codebase. `Application_Status__c` gets set to a submission-indicating value from **at least three separate Apex call sites**: `ApplicationRequirement.cls` (two places), `ApplicationChecklist.cls`, and `ApplicationChecklistComponentController.cls`. The actual "submitted" value is **not hardcoded** — it's read from `Application_Control__c.Submit_Status__c` (configurable per application type), which shares the `Application_Status` global value set with `Application__c.Application_Status__c`.

- **All three known call sites perform sparse updates** — `update new Application__c(Id = ..., Application_Status__c = ...)` — so a trigger on `Application__c` will NOT have `Contact__c`/`Application_Control__c` populated on `Trigger.new`/`oldMap`; it must re-query.
- **The detection mechanism deliberately reacts to the data change itself** (an `after update` trigger comparing old vs. new `Application_Status__c` against the row's configured `Submit_Status__c`), not to any particular Apex method being called — this is resilient to all three call sites and any future ones without needing to touch them.
- `Application_Control__c` on `Application__c` is an **optional** lookup — always null-check before comparing `Submit_Status__c`.
- `ApexPages.currentPage().getHeaders()` **is** accessible from inside a trigger fired synchronously by a VF-page-driven `update` DML (confirmed via live spike) — but only in that synchronous, same-transaction context. It is NOT available later inside an `@future` method dispatched from that trigger (see the global skill's callout-after-DML section) — headers must be captured in the trigger and passed as primitives.

## Testing Conventions for This Project

- **All Apex unit test classes must use a `_TEST` suffix** (e.g. `ApplicationRegistration_TEST`), per CumulusCI convention — not `ClassNameTest` or `TestClassName`. Explicit standing instruction from the project owner (2026-09-18).
- **All Apex test classes live in `force-app/test/default/classes/`, NOT `force-app/main/default/classes/`.** This is a separate, pre-existing package location in this repo (not registered as its own entry in `sfdx-project.json`, but still deployable since `sfdx-project.json`'s single `force-app` package directory entry covers everything under `force-app/`, including sibling folders to `main`). The **entire pre-existing EASY test suite already lives here** (`ApplicationRegistration_TEST.cls`, `ApplicationLoginController_TEST.cls`, `ApplicationRequirement_TEST.cls`, and ~40 others) — new test classes must be created directly in this folder, not in `force-app/main/default/classes/` alongside the production code they test.
- **A real regression happened and was fixed during this feature's build (2026-09-21):** fraud-monitoring test classes were initially authored in `force-app/main/default/classes/` (the wrong location) without realizing `force-app/test/default/classes/` existed and already contained same-named classes for two of them. `ApplicationRegistration_TEST` was caught before real damage (deploy failed on unrelated syntax first). **`ApplicationLoginController_TEST` was NOT caught in time and the deploy succeeded, silently overwriting the pre-existing original test class in the org** (an 11KB fraud-monitoring test replaced the original ~3KB `testApplicationLoginController`/`testLoginState` test methods). This was discovered only when moving files into the correct `force-app/test/default/classes/` folder surfaced the pre-existing file still sitting there un-clobbered locally. **Fixed** by restoring the original class from local source (`sf project deploy start` against the untouched local file) and renaming the fraud-monitoring test to `ApplicationLoginFraudCapture_TEST` instead — mirroring the same rename pattern already used for `ApplicationRegFraudCapture_TEST`.
- **Always check `force-app/test/default/classes/` (not just `force-app/main/default/classes/`) for an existing class of the intended name before creating a new test class**, and always query `SELECT Name FROM ApexClass WHERE Name = 'YourIntendedName'` via Tooling API as a second check against the live org — a same-named deploy silently overwrites existing coverage rather than failing loudly, and local-source and org state can each independently miss a collision the other would catch.
- **Apex class names have a 40-character limit** — a descriptive name like `ApplicationRegistrationFraudMonitoring_TEST` (44 chars) will be rejected at deploy time with `Identifier name is too long`.
- **`Application_Setting__c.getOrgDefaults()` in a test context returns a blank in-memory record**, not the real org's configured settings (test contexts never see real data without `SeeAllData=true`, which must never be used). This object has two required fields **unrelated to fraud monitoring** — `Community_Profile_Ids__c` and `Permission_Set_Id__c` — that must be populated with dummy values in any `@TestSetup` that upserts this custom setting, or the upsert fails with `REQUIRED_FIELD_MISSING`. Always `SELECT` (or grep) for all `<required>true</required>` fields on a custom setting before writing test setup data for it — don't assume only the fields your specific test cares about need values.
- **Creating a `User` with a `ContactId` requires a genuine portal-capable Profile** — an internal profile like `System Administrator` fails with `FIELD_INTEGRITY_EXCEPTION: only portal users can be associated to a contact`. Use a real portal profile (e.g. `Customer Community Login User`), and note this also requires the Contact to belong to an `Account` — a bare `Contact` with no `AccountId` is rejected for portal user association.
- **`Site.login()` and `Site.createExternalUser()` cannot be invoked from a standard Apex test context.** Where fraud-monitoring logic sits immediately downstream of one of these calls (`ApplicationLoginController.login()`, `ApplicationRegistration.submit()`), the actual fraud-capture logic was extracted into a separately-testable method/marked `@TestVisible` (`ApplicationLoginController.logLoginAttempt`) or is already a standalone `public static` method (`ApplicationRegistration.logRegistrationAttemptAsync`), and tested directly rather than through the untestable wrapper. `ApplicationRegistration.submit()` additionally has pre-existing test-bypass logic (`if (!Test.isRunningTest() && ...)`) that makes its fraud-capture call site structurally unreachable from any unit test regardless of setup — this is a pre-existing codebase limitation, not something to try to work around.
- **Apex unit test coverage for the fraud monitoring feature is now complete** (task 13, 2026-09-21): 7 test classes, 76 test methods (across all classes including the restored original), 100% pass rate, covering all new/changed classes (`ApplicationReCaptcha`, `ApplicationGeolocation`, `ApplicationEnvironmentCapture`, `ApplicationSharedIpCount`, `ApplicationTriggerHandler`, `ApplicationLoginFraudCapture_TEST` for `ApplicationLoginController`, `ApplicationRegFraudCapture_TEST` for `ApplicationRegistration`). All live in `force-app/test/default/classes/`. See `docs/fraud-monitoring-recaptcha-ip-geo.md`'s task 13 write-up for the full per-class coverage breakdown and rationale for what remains intentionally uncovered.
- **`ApplicationRegistration.page`'s carousel/multi-page-group UI** has a "Single-Page Form" button (`carousel-killer` id) that collapses all question groups onto one page — use this for faster manual/browser-driven testing rather than stepping through the full multi-page carousel. Note: selecting certain dropdowns (term, citizenship) triggers AJAX re-renders that **wipe unrelated form field values already typed** — re-check/re-fill text fields after any dropdown selection, don't fill everything up front then submit.
- **Test credentials/session note:** browser test sessions persist across navigations (cookies retained) — explicitly log out via `/Admissions/secur/logout.jsp` before testing unauthenticated flows like registration after a prior login test.
