# Fraud Monitoring Enhancements: reCAPTCHA v3 + IP/Geolocation Tracking

**Jira:** [ECRMSF-5511](https://stthomas.atlassian.net/browse/ECRMSF-5511) (reCAPTCHA) and [ECRMSF-5529](https://stthomas.atlassian.net/browse/ECRMSF-5529) (IP & Geolocation Tracking), both under epic ECRMSF-1, linked as "clones."

**Status:** Design confirmed with stakeholder (Thad Dahlberg) 2026-09-17. Not yet built. This doc is the source of truth if context/session is lost — re-read this before resuming work.

## Business context

University admissions fraud ring: bad actors complete a full admissions application, get accepted, then use the application fee payment step to test stolen credit card numbers for validity. Real cardholders whose numbers were used then dispute the charges with the university. In some cases, fraudulent applicants have received financial aid before being caught. Per stakeholder Alley B. (Dir. of GR Admissions), this is causing significant operational and reputational impact and consuming substantial manual review time across colleges.

**Goal:** Surface suspicious login/registration/submission activity for staff review. This is explicitly **monitoring only** — no automatic blocking or denial of applications at this stage. International applicants, VPN usage, travel, mobile networks, and shared environments (e.g. campus computer labs) can create legitimate false positives; reviewer training and Flow-tunable thresholds are meant to reduce false-positive fatigue, not remove human review.

## Confirmed design decisions

1. **Capture frequency: every event, not just first registration.** reCAPTCHA validation and environmental-variable (IP/geo/browser/OS) capture happen on account registration, **every login**, and **every application submission**. Rationale (stakeholder): fraud can be committed by a bad actor after initial legitimate registration, via stolen credentials or a hijacked session — capturing only at registration would miss this entirely.
2. **reCAPTCHA v3 free tier, must degrade gracefully.** Using Google's free reCAPTCHA v3 tier initially; leadership will decide later whether the paid tier is worth it based on real usage/testing. The free tier has a request quota. When quota is exhausted or the API call fails for any reason:
   - Never block the user's registration/login/submission.
   - Never treat "score unavailable" as equivalent to "high risk" (i.e. do not silently write 0.0 or treat null as suspicious).
   - Store a nullable score plus a separate status field (`Scored` / `Unavailable` / `Error`) so downstream Flow/LWC logic can tell "no data" apart from "confirmed high risk."
3. **Location-match warning logic lives in a Flow, not Apex.** The comparison between submission-IP-derived geolocation and the applicant's mailing address, and the shared-IP-count threshold that triggers a "warning," need ongoing fine-tuning by admins (tolerance, thresholds) without a full deploy cycle. Apex's job is limited to populating raw data (IP, geolocation string, mailing address already exists on Contact/Application). A record-triggered Flow does the actual comparison and sets warning flags/text.

## Data model

### New object: `Application_Login__c`

One row is written for **every** Registration, Login, or Submission event, for **every currently-active `Application__c`** the acting Contact has (a user may have multiple active applications attached to their portal account — e.g. applying to multiple colleges/programs). This means a single login event can produce multiple `Application_Login__c` rows if the Contact has multiple active applications. Lookup-based (not a junction object) per stakeholder preference — enables a native related list on the Application page layout without building a custom LWC list view (though an LWC surfacing summarized signals is still planned, see below).

Relates off **Contact**, not User — confirmed via Jira comment on ECRMSF-5541: *"Created off contact, could not create tied to user."* This is consistent with the existing codebase, where `ApplicationRegistration.cls` and `ApplicationLoginController.cls` already operate against Contact/Site guest-user patterns, and `Application__c` already has a `Contact__c` lookup.

| Field API Name | Type | Notes |
|---|---|---|
| `Contact__c` | Lookup(Contact) | The acting Contact |
| `Application__c` | Lookup(Application__c) | The specific active application this row is tied to |
| `Event_Type__c` | Picklist (Registration / Login / Submission) | |
| `ReCAPTCHA_Score__c` | Number(2,2), nullable | 0.0–1.0 per Google's v3 scoring; null when unavailable |
| `ReCAPTCHA_Score_Status__c` | Picklist (Scored / Unavailable / Error) | Distinguishes "no data" from "confirmed low score" |
| `IP_Address__c` | Text | From request headers (see Environmental Variable Capture below) |
| `Geolocation__c` | Text | Format: "City, State/Province, Country" (per ticket spec, e.g. "Minneapolis, Minnesota, United States") |
| `Browser__c` | Text | Parsed from User-Agent |
| `Operating_System__c` | Text | Parsed from User-Agent |
| `Device_Type__c` | Text/Picklist | Desktop / Mobile / Tablet, parsed from User-Agent |
| `User_Agent_Raw__c` | Long Text Area | Raw header value, kept for audit/re-parsing if parsing logic improves later |
| `Client_Env_JSON__c` | Long Text Area | JSON blob of client-only signals collected via JS (timezone, screen resolution, language, platform) — see Environmental Variable Capture below |

### `Application__c` additions (fraud review + warning fields, per ECRMSF-5529 field spec)

| Field API Name | Type | Notes |
|---|---|---|
| `Fraud_Review_Status__c` | Picklist | Values: Review Recommended, Under Review, Confirmed Fraudulent, Cleared/Legitimate, Unable to Confirm |
| `Fraud_Review_Notes__c` | Long Text Area | Free-text staff notes |
| `IP_Location_Match_Warning__c` | Checkbox | Set by Flow, not Apex |

| `Shared_IP_User_Count_30Day__c` | Number | Apex-calculated aggregate; count of distinct Contacts sharing the same submission IP in the trailing 30 days |
| `Shared_IP_Warning__c` | Checkbox | Set by Flow based on the count above vs. an admin-tunable threshold |

## reCAPTCHA v3 implementation

Reference pattern: [Summit-Events-App](https://github.com/SFDO-Community/Summit-Events-App) `SummitEventsRegisterController.cls`, which already implements Google reCAPTCHA v3 in a Visualforce+Apex context (same platform constraints as EASY).

- **Settings**: extend `Application_Setting__c` with `reCAPTCHA_Site_Key__c`, `reCAPTCHA_Secret_Key__c`, `reCAPTCHA_Library_Url__c`, `reCAPTCHA_Endpoint__c` — mirrors Summit Events' `Summit_Events_Settings__c` fields.
- **Utility class**: new `ApplicationReCaptcha` (or similar) Apex class with a static method (e.g. `isReCAPTCHAValid(String token)`) that calls Google's siteverify endpoint and returns a wrapper with score + status. Summit Events' pattern uses a `-1` sentinel Decimal for endpoint/auth failure; our design additionally needs an explicit status enum since we must NOT treat "unavailable" as "low score" (see Decision #2 above) — a bare `-1` sentinel risks being misread as "very suspicious" by anyone later writing Flow logic against the raw number, so the separate `ReCAPTCHA_Score_Status__c` field is required in addition to (not instead of) a sentinel value.
- **Remote Site Setting / CSP Trusted Site** required for the reCAPTCHA verify endpoint domain. Deployed as `force-app/main/default/remoteSiteSettings/Google_reCAPTCHA.remoteSite-meta.xml`, URL `https://www.google.com`. **This was missed in the initial build and caused a real, hard-to-diagnose bug**: without it, the Apex `Http.send()` callout to the siteverify endpoint throws a `CalloutException`, which `ApplicationReCaptcha.cls`'s try/catch correctly (by design) downgrades to `Unavailable` — meaning the *entire feature silently looked broken* (score always `Unavailable`) with no visible error anywhere, since the graceful-degradation contract intentionally swallows callout failures. Confirmed fixed 2026-09-17 via live login test — `ReCAPTCHA_Score__c` populated with real scores (0.9) immediately after the Remote Site Setting was deployed.
- **Google Cloud Fraud Defense migration confusion (resolved):** Google is currently mid-migration, pushing new key registrations through a "reCAPTCHA Enterprise" / "Fraud Defense" Cloud Console flow by default, which uses a completely different client JS API (`grecaptcha.enterprise.execute()`, not `grecaptcha.execute()`) and a different server-side verification API (Google Cloud REST, not the classic `siteverify` POST) - incompatible with this design's classic v3 implementation and Enterprise requires GCP billing, conflicting with the "free tier" decision. Symptom when an Enterprise key/URLs were accidentally used: browser console error `Uncaught TypeError: grecaptcha.ready is not a function`. Fixed by using classic reCAPTCHA v3 registration/URLs instead: Library URL `https://www.google.com/recaptcha/api.js`, Endpoint `https://www.google.com/recaptcha/api/siteverify` (not `enterprise.js` or a Cloud REST endpoint).
- **Wiring**: both `ApplicationRegistration.cls` (registration) and `ApplicationLoginController.cls` (every login) load the reCAPTCHA v3 JS library on their Visualforce pages (`ApplicationRegistration.page`, `ApplicationLogin.page`), execute client-side, and post the token back via a hidden form field for server-side validation on submit. Score is stored on the `Application_Login__c` row created for that event; **never blocks the action** regardless of score.

## Environmental variable capture (IP, geolocation, browser, OS, device)

**Key constraint discovered during design:** Apex/Visualforce running server-side only has access to HTTP request headers via `ApexPages.currentPage().getHeaders()`. This provides:
- `X-Forwarded-For` — client IP, but can contain multiple hops and is spoofable
- `X-Salesforce-SIP` — Salesforce's own detected source IP header, generally more reliable
- `User-Agent` — raw string; Apex has no built-in parser, so browser/OS/device-type extraction requires either a regex-based parser class or a simple lookup table for common patterns
- `Referer`

Apex/Visualforce has **no access** to screen resolution, timezone, browser language, platform/OS reported by `navigator`, connection type, or any browser-fingerprinting-style signal — those only exist in the DOM/JS runtime, never reach the server as headers.

**Design:** Since reCAPTCHA v3 already requires a client-side JS call (`grecaptcha.execute()`) that posts a token back via a hidden field, piggyback the additional env-var collection on the same JS execution:
1. A small JS snippet (added alongside the reCAPTCHA integration on `ApplicationRegistration.page` and `ApplicationLogin.page`) collects `Intl.DateTimeFormat().resolvedOptions().timeZone`, `screen.width`/`screen.height`, `navigator.language`, `navigator.platform`, and any other cheap/available signals into a JSON object.
2. That JSON is written into a second hidden form field (e.g. `clientEnvJson`) alongside the reCAPTCHA token field, and submitted together on the existing form post — no extra round-trip or AJAX call needed.
3. Apex reads: IP from `X-Salesforce-SIP`/`X-Forwarded-For` headers, browser/OS/device from `User-Agent` parsing, and the JSON blob is stored as-is in `Client_Env_JSON__c` on `Application_Login__c` for now (future work could promote specific fields out of the JSON if reporting demands it, but the ticket's ask — "log more than just location" — is satisfied by capturing the blob).

This same JS-based approach must also run wherever the application submission flow lives (see below) — the submission page will need the same hidden-field JS treatment even though it doesn't use reCAPTCHA, since it still needs the client-only env vars, or the submission-related `Application_Login__c` row will simply have a smaller reliable field set (IP + UA-derived data only, no client JSON) — this decision needs to be made per which VF page actually renders the final "Submit" action (see below).

### Expanded signal set (task 8, added 2026-09-18)

While testing this feature end-to-end via browser automation over the course of this session, several additional cheap, fraud-relevant environmental signals were identified that the original design missed — notably that **automated/bot browsers (including the very Playwright tooling used to test this feature) set `navigator.webdriver = true`**, a signal we were not capturing despite it being one of the most direct automation tells available. Added to `collectClientEnv()` on both `ApplicationRegistration.page` and `ApplicationLogin.page` (kept identical on both pages):

| Signal | Source | Why it matters |
|---|---|---|
| `timezoneOffsetMinutes` | `new Date().getTimezoneOffset()` | Numeric cross-check against the IANA `timeZone` string — a mismatch between claimed zone name and actual UTC offset is a spoofing tell. |
| `languages` | `navigator.languages` (full array, joined) | The singular `navigator.language` was already captured; the full list can reveal inconsistent locale claims. |
| `userAgentJs` | `navigator.userAgent` (client-reported) | Compared server-side against the `User-Agent` *header* Apex already reads — a mismatch between the two is a classic bot-framework tell (see `userAgentMismatch` below). |
| `webdriver` | `navigator.webdriver === true` | **The single most direct automation/bot-detection signal available client-side.** Selenium/Playwright/Puppeteer all set this unless deliberately evaded. Confirmed via live testing that this session's own Playwright-driven test traffic reported `webdriver: false` for this particular MCP driver configuration — worth noting this signal is not universally reliable against all automation tooling, but it is free to collect and still catches a meaningful share of naive bots. |
| `hardwareConcurrency` | `navigator.hardwareConcurrency` | CPU core count; unusual/default values are sometimes seen in headless or bot-farm environments. |
| `deviceMemory` | `navigator.deviceMemory` | Same rationale as above; not available in all browsers (Safari omits it), stored as `null` when absent. |
| `connectionType` | `navigator.connection.effectiveType` | Network type (e.g. `4g`); not available in all browsers, stored as `null` when absent. |

**Server-side merge (`ApplicationEnvironmentCapture.mergeServerSignals`):** Two more signals are only available server-side and are merged into the `Client_Env_JSON__c` blob by Apex after the client JSON is received, rather than being added as new dedicated columns (the JSON blob is the existing designated catch-all for exactly this kind of "log more, it's free" signal per the ticket's ask):
- **`referer`** — the raw `Referer` HTTP header. Listed in this doc's original header inventory but never actually wired into any stored field until now — an application submission or login arriving from an unexpected referring domain (rather than direct navigation or a `stthomas.edu` page) is a low-cost signal worth keeping.
- **`userAgentMismatch`** — `true`/`false`/`null` (null when either side is unavailable to compare). Compares the client-JS-reported `navigator.userAgent` (`userAgentJs` in the blob) against the server-observed `User-Agent` header. A mismatch is a stronger automation signal than either value alone — most legitimate browsers report identical values through both paths, so a real difference usually means the client JS environment was tampered with or the two requests didn't actually originate from the same real browser context.

This merge function never throws and degrades gracefully: a null/blank/malformed `clientEnvJson` blob still produces a valid JSON object containing at least `referer` and `userAgentMismatch: null`, rather than losing the whole blob or failing the record insert. Verified via anonymous Apex covering match, mismatch, null-blob, and malformed-JSON cases — all four produced correct, valid JSON output.

**Wiring:** `ApplicationLoginController.logLoginAttempt()` calls the merge synchronously (no callout involved, no transaction constraint). `ApplicationRegistration.logRegistrationAttemptAsync()` (the `@future(callout=true)` method — see the callout-after-DML bug writeup below) receives the raw `Referer` header as an additional primitive parameter (`refererHeader`, captured synchronously in `submit()` alongside IP/User-Agent, since `ApexPages.currentPage()` is not reliably available inside the future context) and performs the merge inside the future method itself, right before geolocation/reCAPTCHA processing.

**Verified working (2026-09-18, live login test):** A real login produced `AL-0000013` with a `Client_Env_JSON__c` blob containing all new fields correctly populated — `userAgentMismatch: false`, `referer` (the login page URL), `connectionType: "4g"`, `deviceMemory: 32`, `hardwareConcurrency: 8`, `webdriver: false`, plus all prior fields. The registration path was not independently re-verified via a full live UI test after this change (identical shared merge logic already covered by the login test + anonymous Apex verification of `mergeServerSignals` itself), since the underlying async dispatch mechanism was already confirmed working in the prior fix.

## Application submission trigger point (the tricky part)

EASY's application submission is **not** a single, clean event with one controller — investigated and confirmed:

- There is **no existing trigger on `Application__c`.** The only trigger in the codebase referencing "Application" (`UserApplicationTrigger`, on `User`) is explicitly marked `// DEPRECATED` and does nothing.
- `Application_Status__c` is set to a submission-indicating value from **at least three separate Apex call sites**:
  - `ApplicationRequirement.cls` — two places, both using a config-driven `appInfo.submitStatus` / `appControl.Submit_Status__c` value, triggered via a `redirectPage == 'submit'` branch and a `finalSubmitApp()` method.
  - `ApplicationChecklist.cls` — `appControl.Submit_Status__c`.
  - `ApplicationChecklistComponentController.cls` — a `submitAppStatus` parameter passed in from the LWC/Aura layer.
- The actual "submitted" status value is **not a hardcoded literal** in any of these — it's read from `Application_Control__c.Submit_Status__c` (configurable per application type/control), though in practice the `Application_Status` global value set contains a `"Submitted App"` active value that is presumably what most configs point to.

**Design decision:** rather than instrumenting all three (or more, if any exist outside `force-app/main/default/classes` search scope) call sites individually — fragile and easy to miss on future changes — build a new **`after update` trigger on `Application__c`** with a lightweight handler class (e.g. `ApplicationTriggerHandler`), following the deprecated-but-present naming convention in this codebase. The trigger detects any row where `Application_Status__c` changed value between old and new, and where the new value matches the *configured* submit status for that application's `Application_Control__c` record (not a hardcoded string comparison) — this makes the fraud-logging hook resilient to the multiple call sites and to future call sites, since it reacts to the data change itself rather than to any particular Apex method being invoked.

**Confirmed via live spike (2026-09-17, scratch org `UST-EASY__dev`):** `ApexPages.currentPage().getHeaders()` **is fully accessible from inside a trigger**, fired synchronously by a Visualforce controller's `update` DML, within the same transaction/request. Verified with a throwaway trigger + controller + page: the trigger context read back the exact same `User-Agent` header value as the calling page controller. Spike artifacts (`SpikeHeaderContextHelper.cls`, `SpikeHeaderContextTest.cls`, `SpikeHeaderContextTrigger.trigger`, `SpikeHeaderContextPage.page`) were deployed, tested, and then destructively removed from both the local source tree and the org — no residue.

**Implication for design:** the planned `after update` trigger on `Application__c` can self-serve `X-Salesforce-SIP`/`X-Forwarded-For`/`User-Agent` headers directly via `ApexPages.currentPage().getHeaders()` inside the trigger itself. No need for calling controllers (`ApplicationRequirement.cls`, `ApplicationChecklist.cls`, `ApplicationChecklistComponentController.cls`) to capture and pass headers through explicitly before their `update` DML — this simplifies the submission-capture design considerably, since the trigger is now a fully self-contained hook point that doesn't require touching any of the three existing call sites.

**Caveat:** this was tested via a real browser-driven Visualforce page load (not anonymous Apex, not a REST/Bulk API-driven update) — matches the actual production call pattern (VF page controller → DML) for all three known submission call sites. If a submission path is ever found that updates `Application_Status__c` via an async context (`@future`, Queueable, Batch, Platform Event-triggered flow, etc.) rather than synchronously within the same VF request, header access would not be available there — current investigation found no such async submission path, but this should be re-verified if one is discovered during implementation.

## IMPLEMENTED AND VERIFIED (2026-09-18): the Application__c submission trigger (task 19's remaining build work)

**Stakeholder question raised and resolved:** before building this, the stakeholder asked whether the detection mechanism could instead be a trigger on `Application_Login__c` rather than `Application__c`, out of concern that another trigger on `Application__c` (which already has many active triggered Flows) could slow those down. Resolved: this isn't actually a viable substitute, since something still has to *detect the submission and create* the `Application_Login__c` row in the first place — a trigger on `Application_Login__c` can only react to a row that already exists, so it can't replace the detection step (though it remains the right mechanism for the *downstream* fraud-alert Flow work in tasks 10/11/17, which does react to newly-inserted rows). The performance concern itself was addressed by keeping the new trigger deliberately minimal: no SOQL/DML beyond one bulk re-query of the changed Ids, no synchronous callouts, and the actual fraud-monitoring work (which does call out) is dispatched via `@future` — a fire-and-forget call that does not extend the triggering transaction. Stakeholder approved proceeding with the lightweight Apex trigger on this basis.

**Built:**
- `ApplicationTrigger.trigger` — a minimal `after update` trigger on `Application__c` that does nothing but delegate to `ApplicationTriggerHandler.handleAfterUpdate(Trigger.new, Trigger.oldMap)`.
- `ApplicationTriggerHandler.cls` — `handleAfterUpdate()` finds rows where `Application_Status__c` changed value in this update, **captures IP/User-Agent/Referer headers synchronously right here** (this is the only place in the whole call chain where `ApexPages.currentPage()` is reliably available — see the future-method caveat below), then re-queries those Ids for `Contact__c` and `Application_Control__r.Submit_Status__c` (necessary because all three known real call sites perform **sparse updates** — `update new Application__c(Id = ..., Application_Status__c = ...)` — so `Trigger.new`/`Trigger.oldMap` do NOT have those fields populated at all). For each row where the new status matches that application's configured submit status, dispatches `logSubmissionAttemptAsync(contactId, applicationId, ipAddress, userAgent, refererHeader)`.
- `logSubmissionAttemptAsync` is `@future(callout=true)`, same pattern and same reason as `ApplicationRegistration.logRegistrationAttemptAsync` (the trigger fires inside the same transaction as the still-uncommitted `Application_Status__c` update, so a synchronous callout would hit the same `System.CalloutException: You have uncommitted work pending` bug fixed in task 6). **Critical detail that was almost missed and then corrected:** `ApexPages.currentPage()` is NOT available inside the future method itself once that later transaction begins — it must be captured synchronously in the trigger and passed in as primitive `String` parameters, exactly mirroring the registration fix's design. An earlier draft of this method incorrectly tried to call `ApexPages.currentPage().getHeaders()` from inside the future method — caught and fixed before deploying.
- There is currently no reCAPTCHA token or client-JS-collected environmental JSON available for Submission events at all, since no Visualforce page in this design yet performs the client-side JS collection for whichever page renders the final "Submit" action (this remains an open item — see below). `ApplicationReCaptcha.isReCAPTCHAValid(null)` is called with a null token, which correctly and gracefully resolves to `Unavailable` with a clear diagnostic message rather than erroring.

**Verified working (2026-09-18, live test in `UST-EASY__dev`):** Ran the exact sparse-update pattern the real call sites use (`update new Application__c(Id = ..., Application_Status__c = 'Submitted App')`) against a real test Application via anonymous Apex. Confirmed: the trigger fired, correctly identified the status change, re-queried and matched against `Submit_Status__c`, and dispatched the async job — which completed with 0 errors and produced `AL-0000014` (`Event_Type__c = "Submission"`, correctly scoped to the real Contact/Application). Since anonymous Apex has no HTTP request context, this test also exercised the graceful-degradation path end-to-end: `ReCAPTCHA_Score_Status__c = "Unavailable"` with diagnostic `"No reCAPTCHA token was provided by the client."`, `IP_Address__c = null`, `Client_Env_JSON__c = {"userAgentMismatch":null,"referer":null}` — no errors, no blocked update, everything nullable exactly as designed. A real browser-driven submission (through the actual multi-step application requirements UI) would populate IP/UA/Referer from the real VF request context, the same way the Login and Registration paths already do — not independently re-verified via a full UI walkthrough in this session, since the header-capture code path is identical to the already-proven Registration/Login implementations and the harder-to-verify part (the trigger's data-change detection and sparse-update re-query) was the part actually tested here.

**Remaining known gap (unchanged from the original design note, restated for clarity):** the submission event still has no client-side JS hook anywhere, so `Client_Env_JSON__c` for Submission rows will only ever contain the server-merged `referer`/`userAgentMismatch` keys (both frequently null/unknown, since `userAgentMismatch` needs a client-reported UA to compare against) — never the richer signal set (`timeZone`, `webdriver`, `screenWidth`, etc.) that Registration/Login rows get. Fixing this requires identifying which Visualforce page actually renders the final "Submit" button across the three known call sites and adding the same JS collection pattern there — not yet investigated as part of this task, flagged as a distinct follow-up.

## Fraud alerting

- **Location Match Warning Flow** (record-triggered, on `Application_Login__c` insert where `Event_Type__c = 'Submission'`, or on `Application__c` update): reads Apex-populated submission-IP geolocation and the Contact's mailing address, applies admin-tunable comparison/tolerance logic, sets `IP_Location_Match_Warning__c` and `IP_Location_Match_Details__c` on `Application__c`. Compares against **submission IP only**, not login IP — per a resolved Jira comment thread on ECRMSF-5532 (Farrah Friedrich: "it makes the most sense to compare against the application submission IP only... login activity could introduce extra noise/complexity").

### IMPLEMENTED AND VERIFIED (2026-09-21): Location Match Warning Flow (task 17)

Built `Location_Match_Warning.flow-meta.xml`, a record-triggered Flow on `Application_Login__c` (after-save, `Create` trigger type), entry condition `Event_Type__c = 'Submission'` AND `Geolocation__c` is not null - the null-geolocation exclusion matters because a blank `Geolocation__c` means the geo lookup itself was `Unavailable` (see the graceful-degradation contract), and that must never be treated as "confirmed mismatch" by omission.

**Key design decision made during the build:** the original design doc's data model section assumed `Contact` would have standard `MailingCity`/`MailingState`/`MailingCountry` fields available for comparison against `Application_Login__c.Geolocation__c` (a text string like "Minneapolis, Minnesota, United States"). Investigation found the org's `Contact` object also has custom `Mailing_Lattitude__c`/`Mailing_Longitude__c`/`Geolocation_Coordinates__c` formula fields intended for distance-based geo math - but these were explicitly **not** used for this Flow's comparison, because they use `formulaTreatBlanksAs: BlankAsZero`. A Contact with no mailing address on file at all would have these fields silently read as literal `0, 0` (a real point in the Atlantic Ocean), which would make **every** real-world submission IP look "very far away" - a serious false-positive trap that would have made this feature actively harmful for the very population (international applicants, no permanent address yet, etc.) the design doc already flagged as legitimate-false-positive risks. Used the standard `MailingCity`/`MailingState`/`MailingCountry` text fields instead, with an explicit `Applicant_Has_Mailing_Address` formula gate that skips the comparison entirely (no warning, ever) when the Contact has no city or country on file - this is the Flow's single most important safety property.

**Comparison logic** (all Flow formula resources, admin-editable without an Apex deploy):
- `Applicant_Has_Mailing_Address` - `true` only if both `MailingCity` and `MailingCountry` are non-blank on the related Contact.
- `Geolocation_Mentions_Mailing_City` / `_State` / `_Country` - three independent `CONTAINS(UPPER(...), UPPER(...))` checks, matching if the `Geolocation__c` string contains the Contact's mailing city, state, or country (case-insensitive substring match - deliberately loose rather than exact-equality, since geolocation providers and mailing address data don't always agree on exact formatting).
- `Location_Appears_To_Match` - `true` if **any** of the three above match (an OR, not an AND) - intentionally permissive to minimize false positives; a submission from the applicant's home country but a different city within it is not flagged, matching the spirit of "reduce false-positive fatigue" from the design doc's stated goals.
- On no match (and only when a mailing address exists at all), sets `IP_Location_Match_Warning__c = true` and `IP_Location_Match_Details__c` to a formula-built string in the ticket's example format: `"Submission IP Location: {geolocation} | Mailing Address: {city}, {state}, {country}"`.

**Structural gotcha hit and fixed during the build:** an `Update Records` element cannot combine `inputAssignments` (field-by-field updates) with `inputReference` (updating an entire previously-queried record variable) - Salesforce rejects this combination at deploy time with `"You can't use the sObjectInputReference field with the inputAssignments field."` Fixed by filtering the Update Records element by `Id = {!Get_Application.Id}` instead of referencing the queried record directly.

**Deployed clean, 1/1, 0 errors.** **Verified via anonymous Apex with savepoint/rollback** (no permanent data changes) covering three cases:
1. **Mismatch** - Contact mailing address set to Lagos, Nigeria; a Submission-type `Application_Login__c` row inserted with `Geolocation__c = "Minneapolis, Minnesota, United States"`. Result: `IP_Location_Match_Warning__c = true`, `IP_Location_Match_Details__c = "Submission IP Location: Minneapolis, Minnesota, United States | Mailing Address: Lagos, , Nigeria"` - correct format, matches the ticket's example.
2. **Match** - Contact mailing address set to Minneapolis, Minnesota, United States (via `MailingStateCode`/`MailingCountryCode` - this org has state/country picklists enabled, so the free-text `MailingState`/`MailingCountry` fields must be set indirectly via the code fields, not written to directly); Submission row geolocated to the same city. Result: `IP_Location_Match_Warning__c = false` - no false positive.

### IMPLEMENTED AND VERIFIED (2026-09-21): Fraud Alert Flow (tasks 10/11, combined per stakeholder decision)

**Flow design** (`Fraud_Alert.flow-meta.xml`, record-triggered on `Application_Login__c` after-save Create, entry condition `Event_Type__c = 'Submission'`):
1. Gets the related `Application__c` (and via `storeOutputAutomatically`, its `Contact__r` mailing address fields for the location check) and the org's `Application_Setting__c` defaults.

This does mean the comparison logic now exists in two places (this Flow and `Location_Match_Warning`) rather than one - a real but accepted tradeoff, documented here so any future threshold/matching tuning change is applied to BOTH Flows, not just one.

**Other Flow-formula gotchas hit and fixed during the build:**
- Comparing a picklist field (`ReCAPTCHA_Score_Status__c`) directly against a string literal in a Boolean formula expression fails deploy (`Field $Record is a picklist field. ## IMPLEMENTED AND VERIFIED (2026-09-21): Fault-handling for the Fraud Alert Flow (post-completion hardening)

After the feature was declared complete (task 14), a follow-up review asked whether `Fraud_Alert.flow-meta.xml` had adequate fault paths. It did not - as originally built, none of its `recordLookups`, `recordUpdates`, or its `emailSimple` action call had a `faultConnector` at all, meaning any internal failure (a lookup finding no rows, a future validation rule conflicting with a Flow-driven update, an email-sending failure) would cause the Flow interview to fail silently with no record of what happened and no notification to anyone. For a fraud-monitoring system whose entire purpose is making sure a human finds out about something suspicious, a silent failure here is the worst possible outcome.

**New fields added:**
- `Application__c.Fraud_Alert_Processing_Error__c` (LongTextArea 32768) - system-populated diagnostic detail when the Flow hits an internal error. Deliberately separate from the staff-authored `Fraud_Review_Notes__c` so system-generated fault detail is never confused with or overwritten by staff notes.
- `Application_Setting__c.Fraud_Alert_Technical_Contact_Email__c` (Text 255) - a fixed technical/admin contact address, notified only when the Flow itself breaks internally. Deliberately kept separate from `Fraud_Alert_Recipient_Emails__c`, which is for actual fraud-signal matches - different audience, different purpose.

**Fault-path design added to the Flow:**
- Both `recordLookups` (`Get_Application`, `Get_Settings`) now have a `faultConnector` routing to a dedicated `Get_Settings_For_Fault_PreLookup` lookup (a second, independent fetch of `Application_Setting__c`, since the main `Get_Settings` lookup may be exactly what failed) which then sends a technical-failure email describing which Application_Login__c record couldn't be evaluated and why. This is genuinely the scariest failure class, since it means the fraud check never ran at all for that submission - it needs to be visible to someone.
- Both `recordUpdates` (`Update_Shared_IP_Warning`, `Update_Fraud_Review_Status`) now have a `faultConnector` routing to a new `Record_Fault_Detail_PostLookup` update, which writes `$Flow.FaultMessage` into `Fraud_Alert_Processing_Error__c` on the affected `Application__c`, then sends a technical-failure email.
- The `Send_Fraud_Alert_Email` action call has a `faultConnector` routing to the same technical-failure email step (see the caveat below on why this specific one is not fully reliable).
- **The Flow was reordered** so `Update_Fraud_Review_Status` (and `Update_Shared_IP_Warning`) run *before* `Send_Fraud_Alert_Email`, not after. This decouples the two outcomes - a failure in the email step no longer prevents the review-status checkbox/field from being set correctly, since that update has already completed by the time the email is attempted.

**Critical pre-existing bug found and fixed along the way (unrelated to fault-path work, but blocking verification of it):** `Meets_Shared_IP_Threshold` had **no `defaultConnector` at all** - only a `defaultConnectorLabel` with no actual `<defaultConnector>` element. This meant that whenever the shared-IP count was *below* the warning threshold (the normal, common case for the vast majority of submissions), the Flow interview simply **ended immediately after that decision** and never went on to evaluate the reCAPTCHA-below-threshold or location-mismatch signals, and never reached `Update_Fraud_Review_Status` at all. In other words: **since the Fraud Alert Flow was first built (tasks 10/11), it had only ever been evaluating the Shared-IP signal correctly - the reCAPTCHA and location-mismatch signals were silently never being checked**, for any submission that didn't already trip the shared-IP threshold. This was a real, undiscovered regression in previously-verified functionality, not a hypothetical risk. Fixed by adding the missing `<defaultConnector><targetReference>Any_Fraud_Signal_Tripped</targetReference></defaultConnector>`, deployed, and confirmed via anonymous Apex that all three signals are now correctly evaluated regardless of the shared-IP outcome.

**Fault-path verification results:**
1. **`recordUpdate` fault path - verified working.** A temporary, narrowly-scoped validation rule (`TEMP_Force_Fraud_Alert_Fault_Test`, gated on a sentinel string in `Fraud_Review_Notes__c` combined with `ISCHANGED(Fraud_Review_Status__c)` so it only ever fires on the Flow's own update attempt, never on the initial record insert) was used to force a genuine DML fault via anonymous Apex with a savepoint/rollback. Confirmed: `Fraud_Alert_Processing_Error__c` was correctly populated with the exact fault message, `Fraud_Review_Status__c` correctly stayed `null` (the failed update didn't partially apply), and - critically - **the triggering `Application_Login__c` insert itself succeeded without any exception propagating up**, exactly the intended graceful-degradation behavior. The temporary validation rule was destructively removed from both the org and local source immediately after verification.
2. **`emailSimple` fault path - a real platform limitation was found, but it does not create an actual gap in this feature.** Testing this by directly and synchronously inserting an `Application_Login__c` row in anonymous Apex (bypassing the real async architecture) produced an **uncaught** `System.DmlException` (`CANNOT_EXECUTE_FLOW_TRIGGER`, `"Probably Limit Exceeded or 0 recipients"`) - this is a well-documented Salesforce platform behavior where certain `emailSimple` failure classes (most likely here: this scratch org's daily email-recipient limit being exhausted by this session's and prior sessions' extensive live testing) surface as **unhandled faults even with a `faultConnector` present**. This is a known, documented Salesforce platform quirk, not a mistake in this Flow's design - re-confirmed via web research showing this exact error/message pattern reported by multiple other Salesforce practitioners under the same conditions.
   - **However**, re-testing through the *actual* production code path - updating `Application__c.Application_Status__c` via the same sparse-update DML pattern the real call sites (`ApplicationRequirement.cls`, etc.) use, letting `ApplicationTrigger`/`ApplicationTriggerHandler` dispatch the `@future(callout=true)` async method exactly as designed - confirmed the applicant-facing update **always succeeds**, regardless of whether the Fraud Alert Flow's email step fails internally. Two independent reasons why: (a) the `Application_Login__c` insert and the Fraud Alert Flow it triggers happen inside the separate `@future` transaction, entirely decoupled from the original synchronous status-update transaction that the applicant is actually waiting on; and (b) `ApplicationTriggerHandler.logSubmissionAttemptAsync` already wraps its own `insert logEntry;` call in a `try/catch` that catches exactly this kind of exception (confirmed this pre-existing `try/catch`, not the Flow's own fault connector, is what actually stops the exception from propagating in this scenario). The same pattern was confirmed present in `ApplicationLoginController.insertLoginRecords` and `ApplicationRegistration.logRegistrationAttemptAsync` - all three real insert call sites already have this defensive layer, built during earlier sessions, independent of today's fault-path work.

**Conclusion / lesson for future Flow work in this codebase:** the Flow's own fault connectors are the correct, working, primary mechanism for `recordLookup` and `recordUpdate` faults (proven above). For `emailSimple` specifically, a `faultConnector` is **necessary but not sufficient** - certain failure classes can bypass it entirely due to platform behavior outside this Flow's control. This does not create a real gap here only because the *calling* Apex code already wraps its `Application_Login__c` insert (the DML that actually triggers this Flow) in its own `try/catch`, providing an independent second layer of protection. **Both layers matter for different reasons**: the Flow's internal fault handling maximizes the chance a human is notified when something breaks; the Apex `try/catch` around the triggering insert is the actual guarantee that a real applicant's login/registration/submission is never blocked by anything going wrong downstream, regardless of whether the Flow's own fault handling manages to catch it.

## Geolocation strategy (hybrid, confirmed 2026-09-18)

**Decision:** Use Salesforce's own `LoginHistory`/`LoginGeo` standard objects for **Login** events (free, no external callout, populated automatically by Salesforce's login pipeline), and a third-party IP geolocation API for **Registration** and **Submission** events (which have no Salesforce-native equivalent, since they are not login actions).

**Why not use `LoginHistory`/`LoginGeo` for everything:** they are populated only by Salesforce's own login pipeline (`Site.login()`, OAuth, standard UI login, etc.) with a `LoginTime`/`UserId` key — there is no equivalent object for a generic "here's an IP, tell me its location" lookup, and no way to write to it or query it against an arbitrary IP that isn't tied to an actual login event. Registration and submission are not logins, so they need a real IP geolocation API regardless.

**Verified schema (confirmed live in `UST-EASY__dev`, 2026-09-18):**
- `LoginHistory` — created for every `Site.login()`-driven Community login (`LoginType = 'Chatter Communities External User'` for portal users, confirmed against real test logins). Relevant fields: `UserId`, `LoginTime`, `SourceIp`, `ForwardedForIp`, `LoginGeoId` (lookup), `Status`, `CountryIso`.
- `LoginGeo` — the actual city/state/country/lat-long detail, reached only via `LoginHistory.LoginGeoId`. Fields: `City`, `Subdivision` (state/province), `Country`, `CountryIso`, `PostalCode`, `Latitude`, `Longitude`. Confirmed populated correctly for a real test login (`City: Minneapolis, Subdivision: Minnesota, Country: United States`) — matches the ticket's required "City, State/Province, Country" format directly.
- **Known platform constraints:** `LoginHistory` cannot have Apex triggers (confirmed: "You can't create a trigger on LoginHistory object" - not something we needed anyway, since we read it, not react to it). It is not directly joinable from custom objects in SOQL; must query `LoginHistory` separately by `UserId` + a `LoginTime` window immediately after `Site.login()` succeeds, then follow `LoginGeoId` to `LoginGeo` in a second query.
- **Known reliability gap (per Salesforce's own KB, article 000386769):** "Login History and LoginEvent object may not have geographical information... for a very small percentage of logins." Not a blocker - already consistent with this design's existing tolerance for `Geolocation__c` being null.

**Design for the Login event path (`ApplicationLoginController.logLoginAttempt()`):** after `Site.login()` succeeds (not before - the LoginHistory row doesn't exist until authentication actually completes), query `LoginHistory` for the just-authenticated user's most recent row, follow `LoginGeoId` to `LoginGeo`, and format the result as `"{City}, {Subdivision}, {Country}"` into `Geolocation__c`. If any part of this lookup fails or returns null (per the known reliability gap), leave `Geolocation__c` blank - never block login on this, same graceful-degradation posture as reCAPTCHA.

**CONFIRMED WORKING (2026-09-18, live test in `UST-EASY__dev`):** Restructured `login()` to call `Site.login()` first and capture its `PageReference` result, then run fraud-monitoring capture (passing whether login succeeded) before returning the already-computed result - this was necessary because the geo lookup needs to happen strictly after authentication completes. Live login test produced `Application_Login__c` record `AL-0000009` with `Geolocation__c: "Minneapolis, Minnesota, United States"` - exact match to the ticket's required format, zero-cost, no external API. A failed login still gets an `Application_Login__c` record (repeated failed-login attempts are themselves a fraud signal worth capturing), just without a geolocation value, since no `LoginHistory` row exists for a failed attempt.

**Design for the Registration/Submission event paths:** Uses ip-api.com's free, non-commercial JSON endpoint via a new shared utility, `ApplicationGeolocation.cls`. **CONFIRMED WORKING (2026-09-18, live callout test in `UST-EASY__dev`):** `ApplicationGeolocation.getGeolocation('24.152.140.219')` returned `"Minneapolis, Minnesota, United States"` - matches the Login-path (`LoginHistory`/`LoginGeo`) result exactly for the same IP, confirming both geolocation sources agree.

Key design points, all driven by ip-api.com's free-tier constraints:
- **Endpoint is plain HTTP, not HTTPS** (`http://ip-api.com/json/{ip}?fields=...`) - free tier has no SSL. Remote Site Setting (`ip_api_com.remoteSite-meta.xml`) has `disableProtocolSecurity: true`, which Salesforce requires explicitly to allow a non-HTTPS callout target at all.
- **Rate limit is 45 requests/minute PER SOURCE IP** - since all of this org's outbound Apex callouts originate from Salesforce's own IP ranges, this budget is shared across ALL registration/submission events org-wide (not per-applicant), a materially tighter constraint than reCAPTCHA's per-key quota. On `HTTP 429`, the method returns `null` immediately rather than retrying or throwing.
- **`status: "fail"` in the JSON body** (not an HTTP error code) signals bad/private/reserved IP or invalid query - checked explicitly, since a 200 OK response can still mean "no data."
- **Non-commercial use only**, per ip-api.com's terms - worth keeping in mind if this ever needs revisiting for a paid/commercial tier at higher volume.
- Same graceful-degradation contract as reCAPTCHA and the Login-geo path: never throws, returns `null` on any failure, and callers must never block registration/submission on the outcome.

**Not yet done:** wiring `ApplicationGeolocation.getGeolocation()` into `ApplicationRegistration.cls` and the submission-capture trigger (task #6, not yet started) - the utility class itself is built and verified, but nothing calls it yet outside of this one-off verification test.

## CRITICAL BUG FOUND AND FIXED (2026-09-18): callouts cannot run synchronously in ApplicationRegistration.submit()

**Root cause:** `System.CalloutException: You have uncommitted work pending. Please commit or rollback before calling out`. Salesforce Apex forbids making an HTTP callout (`Http.send()`) in the same transaction as prior uncommitted DML, unless that DML has already committed. `ApplicationRegistration.cls`'s `submit()` performs multiple DML operations before the account-creation success block (`insert interaction`, `update` on Account, and `Site.createExternalUser()` itself performs DML) - by the time `logRegistrationAttempt()` tried to call `ApplicationReCaptcha.isReCAPTCHAValid()` (an Apex callout) and `ApplicationGeolocation.getGeolocation()` (another callout) in the SAME transaction, both were silently blocked by this platform constraint. `ApplicationReCaptcha.cls`'s try/catch correctly caught this exception and downgraded it to `Unavailable` (working exactly as designed for graceful degradation) - but this meant reCAPTCHA scoring was ALWAYS unavailable for every registration, not just some. This is distinct from the earlier Remote Site Setting bug (that blocked the callout at the network layer; this blocks it at the transaction layer) - both manifest identically as "always Unavailable," which is why it wasn't caught until the new `ReCAPTCHA_Error_Detail__c` diagnostic field (built specifically to debug this class of issue) surfaced the actual exception message on a real test registration (`AL-0000011`).

**Why the Login path was unaffected:** `ApplicationLoginController.login()` calls `Site.login()` FIRST (no prior DML in that transaction up to that point), then does its own DML (`insert` on `Application_Login__c`) only AFTER the callout-dependent work - the callout order relative to DML never violated this constraint there.

**Fix:** Deferred registration's callout-dependent fraud-monitoring work (reCAPTCHA validation + geolocation lookup) to an asynchronous `@future(callout=true)` method, which runs in a new transaction after the current one commits - this is the standard, documented Salesforce pattern for "I need to do DML AND a callout in one logical operation." See implementation in `ApplicationRegistration.cls`.

**Verified fixed via live test (2026-09-18):** After deploying the fix, a fresh registration (Test3 FraudMonitoring3) produced `AL-0000012` with `ReCAPTCHA_Score__c = 0.9`, `ReCAPTCHA_Score_Status__c = "Scored"`, `ReCAPTCHA_Error_Detail__c = null`, and `Geolocation__c = "Minneapolis, Minnesota, United States"` (via ip-api.com) - confirming the async future dispatch resolves the uncommitted-work callout restriction. The `logRegistrationAttemptAsync` AsyncApexJob completed with 0 errors roughly 60 seconds after the registration postback (scratch org queuing latency; production orgs are typically much faster). Task 6 (ApplicationRegistration wiring) is now complete.

## Permission set access model

Three permission sets were updated to grant access to the new object/fields (2026-09-17):

| Permission Set | `Application_Login__c` object | `Application_Login__c` fields | `Application__c` fraud fields |
|---|---|---|---|
| `Application_Community_Guest` | Create + Read (Create requires Read per Salesforce's permission model) | Read+Edit on all non-required fields (guest inserts these directly during registration) | None granted |
| `Application_Community` | Create + Read | Read+Edit on all non-required fields (logged-in user inserts these during login) | None granted |
| `Application_Admin` | Read only (no Create/Edit/Delete — staff never author these records by hand; Apex inserts run in system context, not as the logged-in admin) | Read only on all fields (audit log — even admins shouldn't edit after the fact) | `Fraud_Review_Status__c`/`Fraud_Review_Notes__c`: Read+Edit (staff-managed). `IP_Location_Match_Warning__c`/`IP_Location_Match_Details__c`/`Shared_IP_User_Count_30Day__c`/`Shared_IP_Warning__c`: Read only (Flow/Apex-managed, staff shouldn't hand-edit to preserve signal integrity) |

**Notes on required fields:** `Application_Login__c.Event_Type__c`, `.ReCAPTCHA_Score_Status__c`, `.Application__c`, and `.Contact__c` are all marked `required` at the field level, and Salesforce does not allow (rejects at deploy time) explicit `fieldPermissions` entries for required fields — they are implicitly always accessible to any user who can create the record at all. No permission set entries exist for these four fields; this is intentional, not an oversight.

**Deliberate gap:** Other staff-facing permission sets that also touch `Application__c` (`Application_Reviewer`, `Application_Processing`, `Application_Updates`, `Application_Decision`, `Application_Config_Admin`) were **not** updated as part of this pass — only the three sets explicitly named (Guest, Community, Admin) were addressed. If reviewers/processors using those other sets need to see or work the fraud review fields, that is a follow-up task, not yet done.

**Not yet decided:** Whether `Application_Admin` should also get Delete on `Application_Login__c` for data-retention/GDPR purposes. Left off by default (policy decision, not made here).
